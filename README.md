# injector

**injector** is a command-line tool that generates type-safe dependency-injection (DI) code for Go projects.

Unlike traditional DI frameworks that rely on provider sets or runtime containers, injector uses **Go's type system** plus a small set of struct tags and an optional comment directive to describe dependency injection in a clear and explicit way.

The core idea is simple:

> * The Container declares **what** is exposed.
> * Providers declare **how** values are constructed.
> * injector wires them together at generate time, producing plain Go constructors.

---

## Install

```bash
go install github.com/mickamy/injector@latest
```

## Concept

### 1. Container

A **Container** is a struct that declares what your application exposes. Fields with an `inject:"..."` tag are managed by injector.

```go
type Container struct {
	UserService service.User `inject:""`
}
```

* The presence of any `inject:"..."` tag marks a struct as a container.
* The tag carries a directive that determines the field's role.

### 2. Provider

A **provider** is any top-level function whose result is `(T)` or `(T, error)` and where `T` is a named type, pointer to a named type, or interface.

```go
func NewUser(database *infra.Database) service.User {
	return &user{database: database}
}
```

* Providers are **automatically discovered** during static analysis.
* Dependencies are **inferred from function parameters**.
* No manual registration or wiring code is required.

## Quickstart

Define a container:

```go
package main

import (
	"github.com/example/myapp/config"
	"github.com/example/myapp/service"
)

type Container struct {
	_           config.DatabaseConfig `inject:"with=config.NewReaderDatabaseConfig"`
	UserService service.User          `inject:""`
}

func main() {
	c := NewContainer()
	if err := c.UserService.Register("Alice", "P@ssw0rd"); err != nil {
		panic(err)
	}
}
```

Run the generator:

```bash
injector ./...
```

Result (`injector_gen.go`):

```go
// Code generated by injector. DO NOT EDIT.

package main

import (
	config "github.com/example/myapp/config"
	infra "github.com/example/myapp/infra"
	service "github.com/example/myapp/service"
)

func NewContainer() *Container {
	readerDatabaseConfig := config.NewReaderDatabaseConfig()
	database := infra.NewDatabase(readerDatabaseConfig)
	user := service.NewUser(database)

	return &Container{
		UserService: user,
	}
}
```

## Tag reference

| Tag | Field name | Role |
|---|---|---|
| `inject:""` | exported / unexported | output, auto-resolved by type |
| `inject:"with=Foo"` | exported / unexported | output, provider explicitly chosen |
| `inject:"returns"` | exported / unexported | output that also declares the container's return type |
| `inject:"arg"` | `_` | constructor input parameter |
| `inject:"arg=name"` | `_` | constructor input with explicit name |
| `inject:"arg"` | exported / unexported | constructor input parameter whose value is also stored in the named field |
| `inject:"arg=name"` | exported / unexported | same, with explicit parameter name |
| `inject:"with=Foo"` | `_` | override the provider for this type |
| `inject:"returns"` | `_` | declare return type only (no field stored) |
| `inject:"embed"` | `_` | constructor input whose exported fields are usable as resolution sources |

A blank field (`_`) never appears in the struct literal; only its tag controls behavior.

`with=<ref>` accepts:

- fully qualified: `github.com/me/x.NewFoo`
- package short: `x.NewFoo`
- bare function: `NewFoo` (when unique across all packages)

## Directive reference

```
//injector:container [name=...] [returns=...] [must[=true|false]]
```

Directives are **optional**. They override what would otherwise come from defaults or CLI flags.

| Key | Effect | Default |
|---|---|---|
| `name=NewFoo` | Constructor function name. | `New<UpperFirst(StructName)>` |
| `returns=foo.Foo` | Constructor's return type. | `*<StructName>` |
| `must` / `must=true` | Generate `MustNew*` for this container. | (CLI default) |
| `must=false` | Suppress `MustNew*` even when `--must` is given on the CLI. | (CLI default) |

`returns=` from a directive and `inject:"returns"` on a field cannot be combined on the same container.

---

## CLI reference

```
injector [-v] [--tags=foo,bar] [--must] [-o injector_gen.go] <packages>...
```

| Flag | Description |
|---|---|
| `-o <file>` | Output file name per package. Default `injector_gen.go`. |
| `--tags <list>` | Comma-separated build tags (forwarded to `go list`). |
| `--must` | Generate `MustNew*` for every container in scope. |
| `-v`, `--verbose` | Verbose progress output. |
| `--version` | Print version. |
| `-h`, `--help` | Show help. |

CLI flags are merged **per key** with directive values: a directive that sets `must=false` overrides `--must=true`, while `name=` from a directive coexists with `--must` from the CLI.

## Resolution rules

For each output field of a container, injector chooses a provider in the following priority:

1. **Constructor input** — if any `_ Type inject:"arg"` field has a matching type, the input is used.
2. **Override** — if any field (blank or named) has `inject:"with=Foo"` for that type, the named provider is used. Same-type fields that select different providers are rejected as conflicting.
3. **Embed source** — if any `_ Container inject:"embed"` input exposes an exported field of the requested type, that field is read via `arg.Field`.
4. **By name** — if the field itself has `inject:"with=Foo"`, the named provider is used (and its result type must match).
5. **By type** — otherwise, the unique provider whose result type matches is used. Multiple matches produce an error with candidates listed.

Resolution recurses into the chosen provider's parameters until every dependency is satisfied. Cycles are reported as errors.

### Generation fails when

- a dependency has no provider,
- multiple providers match the same type and no `with=` is given,
- a `with=` reference does not match any provider,
- a `with=` reference matches multiple providers (ambiguous short form),
- multiple `inject:"returns"` fields are declared on a single container,
- both an `inject:"returns"` tag and a `returns=` directive are given on the same container.

## How injector compares to other DI approaches

injector explores a different point in the Go DI design space. It is not intended to replace all existing solutions, but to offer a simpler option under specific assumptions: dependency graphs that are largely type-driven and stable at startup.

### wire

**wire** is a compile-time DI tool that requires explicit provider sets and build functions.

```go
var userSet = wire.NewSet(NewConfig, NewDatabase, NewUserService)

func Initialize() (*Handler, error) {
	wire.Build(userSet)
	return nil, nil
}
```

* Explicit provider registration via `wire.NewSet`
* Clear and reviewable dependency graphs
* Additional DI-specific code to maintain

**injector differs by:**

* Eliminating provider sets and build functions
* Using the container struct itself as the declaration of required dependencies
* Reducing the amount of human-maintained DI code

### fx / dig

**fx** and **dig** provide powerful runtime dependency-injection containers.

* Dependencies are resolved at runtime
* Modules, lifecycle hooks, and dynamic wiring are supported
* Suitable for large or highly dynamic applications

**injector differs by:**

* Having no runtime container
* Performing all resolution at generate time
* Emitting plain Go constructors instead of managing a runtime graph

### samber/do

**samber/do** is a lightweight runtime DI container using Go generics.

```go
do.Provide(i, func(i *do.Injector) (*Service, error) { ... })
svc := do.MustInvoke[*Service](i)
```

* Explicit registration via `Provide`
* Runtime resolution and overrides
* Simple API with type-safe retrieval

**injector differs by:**

* Requiring no registration or injector object
* Treating providers as ordinary functions
* Making the dependency graph visible as generated code

### Summary

| Tool      | Resolution Time | Registration | Runtime Container |
|-----------|-----------------|--------------|-------------------|
| wire      | Generate-time   | Required     | No                |
| fx / dig  | Runtime         | Required     | Yes               |
| samber/do | Runtime         | Required     | Yes               |
| injector  | Generate-time   | Not required | No                |

injector works best when:

* The dependency graph is static at startup
* Simplicity and readability are preferred over flexibility
* DI boilerplate should be minimized
